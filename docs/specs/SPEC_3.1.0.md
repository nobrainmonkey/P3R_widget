## 1. Feature specs

### 1.1 Request (1): 「从头重新安排」, reload the current settings and recompute

**Why the feature is needed (evidence)**
- `requestReplan()` does nothing when the plan is current (`PlannerService.java:744-758`, condition `needsPlan` at :755).
- A current plan never shows `planning` (:318-319).
- Every automatic replan passes the installed plan as `previous` (`:898`). That adds a stability bias over the next 3 days:
  - +2% in the base policy (`Heuristics.java:1051`);
  - `STABILITY_MARGIN` (`Planner.java:42`, used at `:622-631`);
  - `SWITCH_MARGIN` (`Planner.java:48`, `:448-456`).
- That bias is the likely "looks off after changing several settings" effect. Dropping it is the real effect of this feature.
- With time budget left over, planning is deterministic (`Planner.java:301-361`).

**Behaviour (service)**
1. **Reload.** Under `lock`: `model = model.withView(LedgerView.load(ledger, view.rules, wiring.applier))`, the same call as `PlannerService.java:1088/1100`.
   - On `SQLException`, keep the cached view and log.
   - The rule pack is not re-parsed (it is an APK asset).
   - The UI then calls `load()`, which drops leftover optimistic profiles (`HomeActivity.apply`, `:236-260`).
2. **Compute fresh.**
   - Job with `previous = null`.
   - Budget `fullReplanBudget(b) = b > Long.MAX_VALUE/3 ? Long.MAX_VALUE : 3*b`, which is 7.5 s on device.
   - `candidates` stays 4 (it is in `PlanHash`).
   - `options.followUp = true` and `followUpKey = planKey`, so no automatic 2× run follows.
3. **Accept.**
   - If the installed plan is stale, install the result as a normal job would.
   - Otherwise extract `static int compareGoals(Profile, Plan a, Plan b)` from `improves` (`:816-835`). `improves` keeps its behaviour and is rewritten on top of it.
   - `accept = g > 0 || (g == 0 && (!fresh.budgetExhausted || current.budgetExhausted))`.
   - Never call `improves(current, fresh)`.
   - When not accepted: keep the plan, call `followUpDoneLocked`, and report result `KEPT`.
4. **Not a write.**
   - No revision moves, there is no commandId, and nothing goes into 记录历史.
   - `planCurrent` stays true throughout, so widget one-tap 完成 keeps working (`PlanView.java:135`, `PlanWidget.java:193-200`).
5. **Result.** Compare action and side per slot between the plan before the request and the plan after:
   - identical → `UNCHANGED`, otherwise `CHANGED`;
   - plus `KEPT`, `FAILED` and `CANCELLED`.
6. **A write during the run** cancels the computation. The request stays pending and the next job is again a full job for the new revisions.
7. **Import** (`dropPlan=true`) clears a pending request and posts no message.
8. **Failure while the plan is current:** keep the plan, do not set `planErrorZh` or `failedPlanKey`, and report `FAILED`.
9. **Cancel** (「先不算了」):
   - plan current → keep it and report `CANCELLED`;
   - plan stale → a normal job still runs.

**API** (`service/PlannerApi.java`)
```java
default long requestFullReplan() { requestReplan(); return 0; }   // ticket > 0; 0 before onboarding / after a failed load (then = 重试)
default void cancelFullReplan() { }
enum FullReplanResult { CHANGED, UNCHANGED, KEPT, FAILED, CANCELLED }
// Snapshot:
public boolean fullReplanning;            // queued or computing; planCurrent may stay true
public long fullReplanTicket, fullReplanDoneTicket;
public FullReplanResult fullReplanResult; // of fullReplanDoneTicket, or null
```
- `snapshot()` stays lock-free (`:302-324`). Keep the state in an immutable volatile holder.
- Repeated calls while a request is pending return the same ticket.

**ReplanWorker**
- Add `Job.full` and `Job.ticket`.
- `cancelPartial()` cancels the in-flight job only when `!job.full`. `cancelFull()` cancels it only when `job.full`.
- Update the class comment at `ReplanWorker.java:28-30`.
- In `nextJob`, a pending full job takes precedence over a follow-up or a normal job.
- `runEnded` re-schedules while a full request is still pending.

**Loader validation** (`RulesLoader.parseReminders`, after `parseDatingNote`, `RulesLoader.java:170`; fail fast with field paths):
- `id`:
  - unique;
  - matches `^[a-z]+\.[0-9]{2}-[0-9]{2}(\.[a-z0-9_]+)?$`.
- `kind` is one of `class|exam|tv|request|fragment|trip|feature`. The dynamic kinds `doze`, `nurse` and `rescue` live in their own blocks.
- Days:
  - `day` lies in `[firstDay, lastDay]`;
  - `untilDay` is null or ≥ `day`.
- `slot` is `day|eve`.
- Text fields:
  - `zh` is non-empty;
  - `shortZh` is non-empty and ≤ 16 chars;
  - `answerZh` is required for class and exam and absent otherwise;
  - `option` is in 0..4, nonzero for class only.
- `priority` is 1..3.
- `requires` maps a stat id to Lv 1..6.
- `firstEligible` requires `requires`.
- `conf` and `src` follow the Reload policy.
- `doze.days` are sorted, unique, and every one is a school day.
- `rescueGroups`:
  - each group has `count ≥ 1`;
  - each group's `rescueIds` exist in `tartarus.rescues`.

## 8. Addendum (owner directive, after the spec): WP-E 「尽量都体验」 — breadth-first planning

Owner, verbatim: 「另外你在优化的时候应该想一个guide使用者想要什么，就是一个玩家想尽量体验游戏的所有内容，而不是冲10个max然后不理剩下的社群。这时候应该让用户体验和广度优先」.

### 8.1 Behaviour
- New profile setting **安排风格** (`Profile.style`, JSON `"style"`, values `"breadth"` | `"max"`), default **breadth** — also for stored profiles without the key (it is an algorithm change, not a user setting being rewritten).
  - 「尽量都体验」 (breadth, default): 其余社群 (non-goal links) are valued with **diminishing returns per RANK**: unlocking a link (RANK 1) is worth the most, each further rank a little less, and the MAX bonus is moderate (MAX events and the reward item are content too, but must not outweigh breadth). The planner therefore unlocks and advances every link before stacking a few. Tune the curve with benchmarks (start e.g. f(1)=4, f(2)=2, f(3)=1.6, f(4)=1.4, f(5)=1.25, f(6)=1.15, f(7)=1.05, f(8)=1.0, f(9)=0.95, f(10)=0.9 times `W_OTHER`, MAX bonus 2 ranks instead of 6).
  - 「尽量多 MAX」 (max): exactly today's objective (byte-identical plans to before for the same inputs — keep a test).
- Goals (必须/想要) keep **strict priority** exactly as today (`Planner.Pool.compareGoals`), and `PlanValidator` is unchanged. Only the weights of non-goal links (and goals' own per-rank weights stay) change.
- New profiles (onboarding) opt into **all Link Episode tracks** by default when style is breadth (stored profiles are never rewritten). Link Episodes are content the player wants to see.
- `PlanHash`/planId must include `style`.
- Copy (规划设置, a new card at the TOP of the page, before 社群点数): title `安排风格`; options `尽量都体验` — `先把每个社群都解锁、都往上提，再冲 MAX；时间不够时更均衡。` (default) and `尽量多 MAX` — `集中时间把尽量多的社群升到 MAX。`. 规划说明 gets one sentence explaining the default. Follow docs/GLOSSARY_zh.md.

### 8.2 Metrics and acceptance
- `PlanMetrics` gains breadth metrics: links unlocked (rank ≥ 1) / 22, sum of ranks, links at RANK ≥ 5, minimum rank among non-story links, Link Episodes watched. `docs/PLAN_METRICS.md` table (generated by PlanRealPackTest via PlanMetrics) shows them.
- New `engine/PlanBreadthRealPackTest.java` compares breadth vs max on the same starts (new game 4/21 no Persona; mid-game 10/22 with and without goals; 1/8 late start):
  - new game: breadth reaches all 22 MAX whenever max does (allow at most −1);
  - mid-game / late starts: breadth has ≥ unlocked links, a higher minimum rank and ≥ links at RANK ≥ 5 than max, and its rank sum is not more than ~5% lower;
  - goals reach exactly what they reach under max (strict priority unchanged);
  - every plan validator-clean, within the time budget.
- max style: plans identical to the pre-change engine for the same inputs (golden planId test on 3 scenarios).
