## 可验证反例：魅力给零收益社群制造收益

当前 `Heuristics.addCharmGate` 的核心是：

```java
for (int l = 0; l < t.nLinks; l++) {
    if (demand[l] <= 0) continue;
    needed += demand[l];
    valueSum += perMeeting[l] * demand[l];
}
double saved = needed * (1 - 1 / m.charmMult) * 0.5;
```

而规则中 **太阳和恶魔的每级 threshold 全为 0**，`Kernel.meetingsBetween` 对已经建立的太阳 R1→MAX，无论 `mult=1` 或 `mult=1.51` 都需要恰好 9 次。这里没有任何可被魅力省掉的补点见面。

隔离用例：只把太阳选 MUST，`otherLinks=false`，太阳 R1、学力 ≥Lv4，魅力未满；为了把公式隔离到一个社群，可把其他社群在 fixture 中设为 MAX。当前 `needed=9`、`perMeeting=(1,600,000−100,000)/9=166,666.67`；即使日间完全不拥挤，`saved≈1.5199`，最终 `v=0.1×saved×perMeeting×0.5≈12,665.56`，再乘默认 `statWeight=0.7` 后仍给魅力门槛约 **8,865.89** 的正价值。实际能省的见面是 **0**。

正常状态还有额外污染：`prepareDemand` 不按 `wanted` 过滤，`milestone` 在低于 `target` 时先返回 10；未选社群虽 `perMeeting=0`，`demand` 却仍可能大于 0。这些需求又进入 `addCharmGate.needed`，有些已满足前置的未选社群还会进入 `busy0/busy1`。不能把这套比例直接解释成“目标实际会省多少天”。

最小修正建议：

1. 魅力投资只遍历想要提升、非自动且仍有正收益的社群。
2. 对每个社群用同一份 `rank / pts / ready / route / Persona`，分别调用实际 `remainingMeetings`，比较当前倍率与获得魅力 MAX 后倍率，只把整数差计为收益；太阳、恶魔和本来已经逐次升阶的社群因此给 0。
3. 差值乘其实际可替代见面的价值，再按可到达魅力 MAX 的日期与剩余机会折算。保留“晚上投资、不得挤白天”的边界。
4. 独立检查 `prepareDemand` 的未选社群需求；至少别把不计价值的需求用来声称目标日程过载。前置社群需要的少量等级另由 `linkGateBonus` 贡献，不应自动当成对方也要 MAX。

推荐回归：太阳单目标、恶魔单目标、不带 Persona 的点数门槛社群、已经带 Persona 可连续升阶的社群、关闭魅力加成、现有亲密点刚好已足够。前三维是否应训练要以实际节省而非乘法系数本身为准。

## 另一项可验证缺口：考试前后的同一状态没有奖励差别

把“学力 54→55（Lv3）”分别放在 5/17 夜与 5/23 夜：攻略里前者可以满足首考第一的学力条件，后者对首考已经来不及；当前没有任何考试 gate、考试结果 flag、放榜 transition，除了日历容量变化外，两次学力增量的考试价值同为 0。`policy.examTopMult`/`examGoodMult` 虽写在资产里，却没有进入 Java Policy/Model/Kernel。

这是状态建模缺口，不只是分数太低。最小顺序是先补明确的考前需求和已确认的结果，再依据补齐的生效/失效证据决定未来预测。以考试门槛分阶段补学力，比恢复“学力越早满越好”的常数奖励更贴近攻略。

## 不该据攻略直接改的部分

- 全队特性、电影节全员、遛狗全员、打工累计 50,000 日元奖杯都是不同目标。中文路线即使双社交属性已满仍会打工，可能是现金/奖杯需求，不能直接变成每个用户的默认动机。
- 攻略经常带匹配 Persona、选精确答案、免费喝药和在塔内刷足现金。app 默认 Persona NONE、已选目标还带一场亲密度安全余量，得到比攻略更长的保守路线在预期内。比较时先对齐这些条件。
- 中文日程的课堂选项与英语本地化可能不同，个别题目本来也有版本差异；已有官方简中或中文来源优先的策略应保留。不能为套 aqiu 逐字答案而把现有中文覆盖换成英语直译。
- 宿舍女性角色亲密度在来源间有“固定 2”和“考试第一+魅力6才 2、其他 1”的冲突。当前不给额外社群点数比随手加倍率可靠；可先保留属性和所选特性的确定收益。

### 可实现的最小保守语义

若本版本要落实“与已选 MAX 社群相关的宿舍活动也有优先级”，有证据支持的最小数值是 **+1 原始好感下界**，独立于 Persona/魅力/考试倍率。aqiu 的明确值与另一说法的固定2都不低于1；这不等于已经证实真实裸 base 一定是1，应保留来源 `single/conflict`，不要把信心升级为已验证。

- 只对应上述四名女性队友的已建立社群：`rank >= 1 && rank < 10`。可以用已有稳定 partner id 映射 link id，不使用名字模糊匹配。
- 包含她们的两种宿舍 project，不包含集体学习、羁绊剧场、电影、遛狗或普通陪伴。园艺仍需“已准备作物”的现有开关/前提。
- 只有当前下一阶门槛尚缺好感时，这 +1 才有规划价值；缺口已足或 MAX 的社群不再刷好感分。活动实际完成的点数效果独立于用户是否把该社群选成目标；目标只影响评分价值。
- +1 只加到当前 rank 的亲密点，绝不在晚间直接升 rank、不额外占第二时段、不记普通见面次数。保守状态可只保存达到门槛所需部分，不主张真实游戏不会溢出（10/2 的 36/35 恰好说明会超过门槛）。
- 未解锁时是否存入未来好感没有证据，不提前 bank；女皇/永劫开社群前做活动仍可得三维/特性，但不承诺未来 R1 带隐藏点数。
- **第四次及以后仍可增加好感。** 前三次只约束特性 milestone；不能沿用 `used<3` 作为好感适用条件，10/2 第四次料理是直接反例。
- score 应以本次 +1 对当前缺口、下一次可升阶/少占白天的真实收益计入，不给每次宿舍活动恒定大额“社群相关”奖金。属性、特性、好感三项可以相加，但同一个省下的白天不能在多个目标里重复计。

如果暂时只做可靠性最高的现象覆盖，可以先实现风花/由加莉两人，其他两人在同一规则下具备同来源泛化支持；不应把选择范围误写成“只有这两个角色有好感”。在缺少考试结果状态前，不提升为 +2，也不乘 Persona 或 Charm。

建议回归：风花当前只差1点→读书/种菜后晚间不升阶、下次白天可升；当前只差2点→一次+1仍不保证；第四次料理仍有效；已有好感足够时不加score；未开/已MAX不bank；男队友、集体学习不加好感；关闭园艺仍不能安排种菜；选中解锁目标达成后，只有仍有实际社群缺口才继续产生相应价值。
